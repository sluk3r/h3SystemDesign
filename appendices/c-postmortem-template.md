# 附录 C：故障复盘模板（橙舟版）

> **本附录定位**：可复用的故障复盘文档结构，配套本书的故障观（第 5 章）使用。
>
> "橙舟版"意味着：模板预设了本书的人物、服务、事故年表的约定——你直接拿去给一家虚构（或真实）的公司用，把对应的占位符替换掉即可。
>
> **配套阅读**：第 5 章 5.3（故障分级与应急响应）· 第 5 章 5.4（经典事故案例库）· [设定圣经 §6 历史事故锚点](../chapters/SETTING.md#6-历史事故锚点)

---

## C.1 模板使用守则

**写复盘的目的是预防下一次故障，不是追责。** 这一点写在最前面，不是空话——它直接决定了下面每一栏的填法。

写之前自检三件事：

1. **复盘人不是值班人**。值班人累了一夜，让另一个人主笔——避免"为自己开脱"的盲区。
2. **不要在 24 小时内交终稿**。事故当夜出"快报"（影响 + 时间线 + 已止损），48-72 小时内出"正式稿"（含根因 5 Whys + 改进措施）。
3. **改进措施必须有 owner 和 due date**。没有这两项的"改进措施"半年后回头看是 0% 落地。

---

## C.2 复盘文档结构

下面这一份是橙舟内部用了 5 年的标准结构。每一节的写法在 §C.3 详述。

```
1. 故障摘要（1 段）
2. 时间线（表格）
3. 根因分析（直接原因 + 根本原因 + 5 Whys）
4. 影响评估（用户 / 业务 / 技术 / 组织）
5. 改进措施（短期 / 中期 / 长期，含 owner + due date）
6. 经验教训（做得好的 / 可改进的）
7. 附录（trace / 监控截图 / 关键日志）
```

## C.3 各节写法详述

### 1. 故障摘要

一段话 100-300 字。第一句话是结论，后面是关键数字。

> **范例（基于 SETTING §6 的"2018-03 缓存血案"）**：
>
> 2018 年 3 月 12 日凌晨 02:14 至 02:57，受 Redis Cluster 槽位变更操作影响，缓存集群约 18% key 短时不可达，引发上游订单、商品、用户三大域服务回源数据库，DB 被 100x 流量打挂。事故持续 43 分钟，期间订单创建成功率从 99.9% 跌至 23%，影响约 47 万次下单，直接 GMV 损失约 1.2 亿元。02:57 通过回滚 Redis 配置变更止损，03:42 全部服务恢复至正常水位。事故定级 P0。

**写法要点**：
- 第一句必须包含：时间 + 触发事件 + 影响表现
- 数字必须有：持续时长、影响成功率、GMV 影响（或等价业务指标）
- 不要用"严重影响"这种修辞，用具体百分比

### 2. 时间线

| 时刻（精确到分钟） | 事件 | 操作人 | 备注 |
|---|---|---|---|
| 02:14 | DBA 王姐执行 Redis Cluster 槽位 reshard 操作 | 王姐 | 按月度变更计划进行 |
| 02:15 | order-service 错误率从 0.01% 升至 4% | — | 监控触发了告警 |
| 02:17 | on-call 小赵接到告警 | 小赵 | 第一响应 |
| 02:19 | 小赵在群里 @老张；同时拉应急响应群 | 小赵 | |
| 02:23 | 老张到岗；初步判断"DB 流量异常" | 老张 | |
| 02:31 | 王姐确认 Redis 操作为可疑触发源 | 王姐 | |
| 02:42 | 决定回滚 Redis 配置 | 老张 | 决策点 |
| 02:57 | 回滚完成，错误率回落 | 王姐 | 主止损完成 |
| 03:42 | 各服务水位恢复正常 | — | 完全恢复 |

**写法要点**：
- 必须精确到分钟。"凌晨两点多"不算时间线。
- 必须有"决策点"——谁在什么时候决定做什么。
- 操作人用真名（橙舟版用人物卡里的人）；外部团队用"通信运营商工程师"这种身份描述。
- 不写"我们觉得"、"大家讨论"这种没有 owner 的动作。

### 3. 根因分析

#### 3.1 直接原因（What broke）

一句话讲"哪一行代码 / 哪一个配置 / 哪一次操作"导致的。

> 范例：Redis Cluster 槽位 reshard 期间，约 18% 的 key 在迁移窗口内对客户端不可达；上游服务的"缓存 miss → 回源 DB"逻辑没有限流和降级。

#### 3.2 根本原因（Why it was possible）

为什么这个直接原因是可能的？这是工程文化和系统设计的问题。

> 范例：
> 1. Redis 变更没有"金丝雀槽位"机制——任何变更都是全量执行
> 2. 缓存 miss 回源没有 per-key 互斥锁——一万次请求同时打到 DB 同一行
> 3. DB 没有连接池上限保护——连接堆积直接打挂数据库进程

#### 3.3 5 Whys

| # | 问题 | 答案 |
|---|---|---|
| Why 1 | 为什么 DB 被打挂？ | 短时回源流量是平时的 100x |
| Why 2 | 为什么回源流量这么高？ | 缓存大量不可达 + 没有 per-key 互斥 |
| Why 3 | 为什么没有 per-key 互斥？ | 上线时认为"缓存够稳"，没必要加 |
| Why 4 | 为什么会认为"缓存够稳"？ | 历史上 Redis 集群 99.99% 可用，只在变更窗口偶发不稳定 |
| Why 5 | 为什么变更窗口的不稳定没有被当作风险？ | 变更流程没有"对调用方影响"的强制评审环节 |

**写法要点**：
- 5 Whys 要追到"流程 / 文化 / 设计原则"层面，不要停在"代码 bug"。
- 如果第 3 个 Why 还在讲代码细节，说明追得不够深。
- 真实的 5 Whys 经常追到"不是技术问题，是组织问题"——这是好事，不是失败。

### 4. 影响评估

| 维度 | 内容 |
|---|---|
| **用户影响** | 47 万次下单失败；约 12 万用户在事故期间二次进入页面；客服工单 800+ |
| **业务影响** | 直接 GMV 损失 ~1.2 亿元；30 天内可观测的复购率下降约 0.3% |
| **技术影响** | DB 主库 OOM 一次；Redis Cluster 配置版本回退；事后清理 Redis 慢查询日志 47GB |
| **组织影响** | 触发跨部门紧急 review；DBA / SRE / 业务三方达成"任何 Redis 变更必须走金丝雀"的硬性规定 |

**写法要点**：
- "组织影响"这一行是橙舟版独有——很多公司的复盘没这一项。它记录"这次事故让我们的合作方式发生了什么变化"，往往是最有价值的部分。
- 用户影响必须有"二阶影响"（如复购率），不能只写"成功率下降"。

### 5. 改进措施

每一条必须有 **owner**、**due date**、**验收标准**。没有这三项的不算改进措施。

| 期限 | 措施 | Owner | Due | 验收标准 |
|---|---|---|---|---|
| 短期（1 周内） | 上线 Redis 变更的"金丝雀槽位"机制：任何 reshard 先在 1 个槽位灰度 30 分钟 | 王姐 | 2018-03-19 | 一次完整的金丝雀流程跑通 |
| 短期（1 周内） | order/product/user 三大域 cache miss 路径加 per-key 互斥锁 | 小林 | 2018-03-19 | code review + 压测验证 |
| 中期（1 个月内） | DB 连接池上限保护：超过 80% 自动拒绝新连接 | 王姐 | 2018-04-12 | 故障演练验证 |
| 中期（1 个月内） | 引入熔断机制（→ 第 6 章 6.3 的引入背景就是这次） | 老张 | 2018-04-12 | 上线 + 一次模拟故障演练 |
| 长期（半年内） | 缓存层多级缓存改造：本地 caffeine + 远程 Redis | 小林 | 2018-09-12 | 至少一个核心服务完成改造 |

**写法要点**：
- "短期"措施在事故后 1-2 周必须完成。如果 1 个月还没完成，说明优先级评估错了。
- "长期"措施必须挂在某个季度的技术规划里，否则 90% 的概率会丢失。
- Owner 是个人，不是团队。"DBA 团队负责" = 没人负责。

### 6. 经验教训

#### 6.1 做得好的

- 02:42 的回滚决策果断，避免了进一步级联放大
- 跨团队的应急响应群在 5 分钟内拉起，沟通顺畅
- 监控告警在事故触发后 1 分钟内捕获到异常

#### 6.2 可以改进的

- 02:14 - 02:31 的 17 分钟内，小赵和老张都没意识到 Redis 操作是触发源——监控的"变更事件流"没有和告警系统打通
- 业务侧没有"降级开关"，回滚 Redis 是唯一止损路径
- 复盘报告写到第 3 稿才追到 5 Whys 的第 5 层——下次复盘可以直接从 Why 5 开始倒推

**写法要点**：
- "做得好的" 一定要写，不是客套——这些是要保留进 SOP 的实践。
- "可以改进的"不是责备具体的人，而是"流程的漏洞"。如果某条改进点必须指向具体某个人，重写它。

### 7. 附录

- 关键 trace（traceID 列表）
- 监控截图（DB 连接数、Redis 命中率、订单成功率三张图）
- 关键日志片段
- 相关 commit / Pull Request 链接
- 事故期间的 IM 群完整记录（脱敏后）

## C.4 故障分级速查（与 §C.1 配套）

> 详见第 5 章 5.3。这里只列对应模板使用的速查。

| 级别 | 触发条件 | 响应时间 | 复盘要求 |
|---|---|---|---|
| **P0** | 全站不可用 / 核心交易链路中断 / 资损 ≥ 100 万 | 5 分钟内拉群 | 必须出正式复盘文档（本模板全部章节） |
| **P1** | 核心服务不可用 / 主要功能受损 / 资损 ≥ 10 万 | 15 分钟内拉群 | 必须出正式复盘文档（本模板全部章节） |
| **P2** | 边缘服务不可用 / 部分用户受损 / 资损 ≥ 1 万 | 1 小时内响应 | 简化版复盘（摘要 + 时间线 + 根因 + 改进措施）|
| **P3** | 性能下降 / 体验下降 / 无资损 | 工作时间内响应 | 不强制复盘，但鼓励写"轻量记录"（一张表） |

## C.5 复盘后的下一步

复盘文档写完不是终点。下面三件事是配套动作：

1. **改进措施进入需求池**：每一条带 owner 的改进措施必须进研发需求池，由 PM/TL 排期。否则六个月后回头看就是 0% 落地。
2. **加入"经典事故库"**：值得反复学习的事故应该被收录（参考本书 SETTING §6 的格式）——一年后新人入职时，事故库就是他最好的教材。
3. **故障演练**：复盘中"做得好的"和"可以改进的"事项，下个季度的混沌工程演练里设计对应场景验证（→ 第 14 章）。

## C.6 反模式：不要写成什么样

| ❌ 反模式 | 为什么不好 | ✅ 替代方案 |
|---|---|---|
| "由于网络抖动导致服务不可用" | 网络抖动不是根因，是借口 | 追问"为什么我们的服务不能容忍 X 秒的网络抖动？" |
| "已加强监控" | 没有 owner 没有 due date 的空话 | "新增监控项 XX，由 YY 在 MM-DD 前上线" |
| "感谢 XX 团队的快速响应" | 复盘不是表彰大会 | 把"快速响应"的具体动作写进时间线 |
| "经验教训：以后变更要更谨慎" | 没有可执行的改进 | "变更流程增加 XX 检查点，由 YY 落实" |
| "根因：人为操作失误" | 这是甩锅，不是根因 | 追问"为什么我们的系统允许这种失误造成这种后果？" |
