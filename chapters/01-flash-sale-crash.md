## 1.1 场景：100 万人抢 1000 台手机

北京时间 23 点 59 分，某电商平台的后台监控大屏上，一条绿色的流量曲线正在缓缓爬升。

23:58 —— 8000 QPS。正常。甚至有点少。

23:59:30 —— 32000 QPS。曲线开始抬头，像一条被惊醒的蛇。运维老张放下手里的咖啡杯，把椅子往前拉了半米。他在这个岗位上干了七年，见过太多次零点。每一年他都告诉自己要镇定，每一年他的心跳都会在那最后三十秒不受控制地加速。

23:59:55 —— 120000 QPS。

曲线不再是曲线了。它变成了一面墙，垂直向上。

此时此刻，100 万用户盯着手机屏幕，拇指悬在“立即抢购”按钮上方三毫米。他们中有提前十分钟就打开页面反复刷新的，有在十个群里发了助力链接的，有花钱买了“代抢服务”的——当然，还有几十万个根本不是人的“用户”：黄牛的自动化脚本，每秒 500 次请求，精确到毫秒地锁定着开抢时刻。

零点钟声敲响。

流量在 300 毫秒内从 12 万 QPS 蹿到了 48 万。大屏上的绿色曲线瞬间变成红色——不是因为报警阈值被触发，而是因为渲染像素跟不上数据更新的速度。

这 100 万人要抢的，是 1000 台限量版手机。

100 万 对 1000。不是“百里挑一”，是“千分之一都不到”。每个抢到的概率，大概和你在自动扶梯上捡到一张没有折角的一百块钱差不多。

站在系统架构的角度看，这时候的架构长这样：

```
用户端（100万+）
    │
    ▼
CDN / DNS（静态资源分流）
    │
    ▼
负载均衡（Nginx，分摊到 50 台应用服务器）
    │
    ▼
应用服务器（Tomcat × 50，处理业务逻辑）
    │
    ▼
数据库（MySQL 主从，1 主 2 从）
```

这是一个“看起来还不错”的架构。50 台应用服务器，Nginx 做了分流，数据库还有主从——放在 2010 年代早期的互联网行业，这个配置足够应付大部分场景了。

老张看着那块红色的大屏，心里知道一件事：问题从来不出在“大部分场景”上。

---

这个场景不是虚构的。过去十五年里，几乎每一家做过秒杀的电商公司都经历过高度相似的夜晚。区别只在于：有些公司那晚过后活下来了，有些没有。

而决定活下来的那一批，都做了同一件事——理解了他们那一夜为什么会死。

这就是本章要做的事：从头到尾走一遍秒杀系统的演化之路。不是告诉你“应该怎么做”，而是让你站在那个凌晨零点的大屏前，作为一个第一次面对 48 万 QPS 的工程师，去经历每一次“先活下来，再想更好的办法”。

我们先从一个最朴素的方案开始看看——在没被流量教育过之前，最直觉的设计长什么样。

## 1.2 朴素方案：`UPDATE stock SET count = count - 1 WHERE count > 0`

如果你是一个刚入职两年的后端开发，接到需求“做一个秒杀功能”，你的第一反应大概率是这样的：

建一张库存表。表结构体面、清晰、无可指摘：

```sql
CREATE TABLE seckill_stock (
    product_id  BIGINT PRIMARY KEY,
    total_count INT NOT NULL,       -- 总库存，1000
    sold_count  INT DEFAULT 0,      -- 已售，从 0 开始累加
    version     INT DEFAULT 0       -- 先不管，后面有用
);
```

然后活动开始的时候，用户点“抢购”，服务端执行：

```sql
UPDATE seckill_stock
SET sold_count = sold_count + 1
WHERE product_id = 1024
  AND sold_count < total_count;
```

执行完 `UPDATE` 之后检查 affected rows。如果返回 1，说明扣减成功，创建订单。如果返回 0，说明库存没了，返回“已售罄”。

没有任何花活。Java 代码大概长这样：

```java
@Transactional
public OrderResult seckill(Long productId, Long userId) {
    int rows = dao.updateStock(productId);
    if (rows == 0) {
        return OrderResult.soldOut();
    }
    dao.createOrder(productId, userId);
    return OrderResult.success();
}
```

五行走完。事务套在外面，失败了自动回滚。逻辑清晰得不能再清晰。

而且，你做过测试：100 QPS 的时候，页面秒开，用户丝滑下单。数据库的 CPU 在 15% 左右晃悠，连接池里的连接大多在睡大觉。你甚至有点膨胀——就这？秒杀也没什么了不起嘛。

你的自信是有依据的。让我们看看 InnoDB 在背后做了什么。

InnoDB 的行锁机制有一个非常优雅的设计：当你执行 `UPDATE ... WHERE product_id = 1024` 时，InnoDB 会对 `product_id = 1024` 这一行加一个排他锁（X-Lock）。后到的 `UPDATE` 发现锁被别人持有着，就乖乖排队——不是轮询，不是自旋，是操作系统级的等待。锁一旦释放，MySQL 的线程调度器会唤醒队列里的下一个等待者，把锁交给它。

这个机制在低并发下近乎完美：
- 不会有超卖——同一时刻只有一个人在改这一行。
- 不浪费 CPU——等待者挂起，不占用计算资源。
- 事务保证原子性——扣库存和创建订单要么都成功，要么都回滚。

而且，这一行的更新是就地（in-place）的，不涉及索引重建，不触发页分裂。一次 `UPDATE` 的执行路径极短：走主键索引找到那一行，加锁，修改字段，写 redo log，返回。在固态硬盘 + 充足内存的机器上，整条路径不超过 1 毫秒。

所以，在 100 QPS 下，这五行走得稳稳当当。每秒 100 个人抢，排队、执行、返回——库存从 1000 一路减到 0，整整齐齐，没有超卖，没有报错。

你甚至可以在 Grafana 上看到一条优美的斜线：sold_count 从 0 匀速涨到 1000，QPS 平稳，延迟稳定在 20ms 以内。

那么问题来了——

100 QPS 是这样。10000 QPS 呢？100000 QPS 呢？

那条查询虽然只花了不到 1 毫秒，但在它执行期间，这一行是被锁住的。1 毫秒看起来很短，但如果在这 1 毫秒里又来了 100 个请求呢？它们不会并行执行——它们会排队。一个接一个。

1 毫秒 × 100 个请求 = 100 毫秒。第 100 个人在数据库连接池里等了整整 100 毫秒才拿到锁。

这不是终点。100 毫秒只是处理时间。请求还在不断涌来。当排队的人超过 100 个、500 个、2000 个……

你能猜到会发生什么吗？

让我们在下一节亲眼看看。

## 1.3 崩溃现场：行锁雪崩

### 00:00:00.000 —— 闸门打开

零点。Nginx 的 access log 开始以每秒 20 万行的速度滚动。50 台应用服务器同时接到洪水般的请求，每一台都兢兢业业地从连接池里借一个数据库连接，开始执行那个我们再熟悉不过的 `UPDATE`。

前几个请求几乎瞬间返回。第 1 个，第 2 个，第 3 个——0.8 毫秒，0.7 毫秒，0.9 毫秒。数据库的 response time 仪表盘上，那条线还趴在 1 毫秒以下，像一个正在装睡的人。

### 00:00:00.050 —— 排队开始

第 50 个请求到了。它执行 `UPDATE` 的时候，发现 `product_id = 1024` 这一行已经被锁了。InnoDB 的锁管理器把它挂到等待队列里，告诉它："等着。"

它没有抱怨。它占着一个数据库连接，安安静静地等。

在最初的几十毫秒里，这个画面是美好的：一个人在改数据，其他人在排队，秩序井然。每个请求轮流拿到锁，执行 1 毫秒，释放锁，下一个顶上。吞吐量稳定在每秒大约 800-1000 个库存扣减。

但请注意一个关键的数字：**每秒只处理 1000 个请求，但每秒进来了 100000 个请求。**

这意味着：每一秒钟，队列里会多出 99000 个人。

### 00:00:00.300 —— 连接池的水位警报

让我们算一笔账。

每个应用服务器配置了一个标准的数据库连接池：最大 100 个连接。50 台应用服务器 × 100 个连接 = 5000 个到数据库的总连接。

MySQL 主库的 `max_connections` 设置为了 2000。

到目前为止一切都在控制范围内。正在排队的请求大约 3000 个，每个占着一个连接，MySQL 的线程数还在 1500 左右。

但是请求在以每秒 100000 的速度涌入。每个请求来了就要从连接池借连接，执行 SQL，等待锁释放。那些拿到锁的幸运儿 1 毫秒就完事了，但那些没拿到锁的——它们占着连接不放，一直在等。

**关键问题来了：一个连接被占住等待行锁的时候，这个连接不能干别的事。**

### 00:00:01.000 —— 撞墙

活动开始后 1 秒。数据库连接池被耗尽。

每个应用服务器的 100 个连接全部处于"等待行锁"状态。再有新请求进来，`dataSource.getConnection()` 返回的不是一个连接，而是一个异常：

```
java.sql.SQLTransientConnectionException:
  HikariPool-1 - Connection is not available,
  request timed out after 30000ms.
```

应用服务器开始报错。不是优雅的"已售罄"，是赤裸裸的 `500 Internal Server Error`。

但这只是第一层。

### 00:00:01.500 —— 线程池连锁崩溃

Tomcat 的请求处理线程池——默认 200 个线程——也在燃烧。为什么？因为那些正在"等待数据库连接"的业务线程并没有释放 Tomcat 的工作线程。它们卡在 `dataSource.getConnection()` 上，不返回，不释放。

200 个 Tomcat 线程 → 全部卡在获取数据库连接 → 没有空闲线程处理新请求 → Nginx 把请求往后排 → 后端的请求队列越来越长。

50 台应用服务器，每台 200 个线程。10000 个线程全部堵在同一个瓶颈上：那一行库存记录的行锁。

### 00:00:02.000 —— 数据库自己也崩了

MySQL 的 `SHOW PROCESSLIST` 输出变得极其壮观：2000 行，每一行的 State 都是 `updating` 或者 `waiting for lock`。

CPU 使用率从 15% 飙到了 100%。不是因为 MySQL 在做有用的计算——它在做上下文切换。2000 个线程互相抢占 CPU，每次切换都伴随着缓存失效和 TLB 刷新。InnoDB 的锁管理器在 2000 个等待者之间奔波，唤醒、检查、重新排队。

MySQL 的 response time 从 1 毫秒变成了 30 秒。即便是那些终于拿到锁的幸运请求，它们的 SQL 执行时间也被膨胀到了秒级别——因为服务器的 CPU 全部被上下文切换吃掉了。

### 00:00:03.000 —— 雪崩

现在整个调用链是这样的：

```
用户 → Nginx (排队) → Tomcat (线程池满) → HikariCP (连接池满) → MySQL (行锁队列 2000+)
```

每一层都在等下一层。用户看到的是白屏、菊花转、最后超时。

但这还不是最糟的。最糟的是：**其他和秒杀无关的业务也挂了。**

为什么？因为它们是同一台数据库。用户浏览商品详情——一个简单的 `SELECT * FROM product WHERE id = 8888`——也需要数据库连接。但连接池已经被秒杀的 100 个连接占满了。这个无辜的查询请求拿不到连接，超时，报错。

首页挂了。购物车挂了。连登录都挂了——因为登录也要查数据库。

一场针对 1000 台手机的秒杀活动，拖垮了整个电商平台。

### 回放分析

用表格回放这 3 秒内的关键事件：

| 时间 | 事件 | 系统状态 |
|------|------|---------|
| 00:00:00.000 | 零点，流量涌入 | 正常 |
| 00:00:00.050 | 行锁排队超过 50 | response time 轻微上升 |
| 00:00:00.300 | 连接池水位 90% | 应用日志出现慢查询告警 |
| 00:00:01.000 | 连接池耗尽 | 应用开始抛连接异常 |
| 00:00:01.500 | Tomcat 线程池耗尽 | 500 大面积出现 |
| 00:00:02.000 | MySQL CPU 100% | 上下文切换风暴，所有 SQL 变慢 |
| 00:00:03.000 | 雪崩 | 整个平台不可用 |

这个崩溃最讽刺的地方在于：**所有请求最终只有一个目的——扣那一行库存。** 真正在"工作"的请求从来没超过 1 个（因为行锁确保了串行执行）。其他 1999 个数据库连接、10000 个 Tomcat 线程、100000 个等待中的 HTTP 请求——全部是无效等待。

它们不干活，只排队。

这就是行锁雪崩的本质：**并发量超过了串行处理能力的上限，系统被自己的"等待管理费用"压垮了。**

---

现在，你知道了为什么会死。接下来要做的事只有一个：让它活下来。

从哪里开始呢？从最显而易见的那件事——让数据库少干点活。

## 1.4 第一次演化：Redis 挡在读前面

复盘那天晚上的日志，团队发现了一个令他们沉默许久的数字：

**到达数据库的所有请求中，87% 是读请求。**

用户打开秒杀页面 → 查商品信息。用户反复刷新 → 查商品信息。用户看库存是不是已经没了 → 查商品信息。用户在等待倒计时 → 还在查商品信息。

这些请求的本质一模一样：`SELECT * FROM product WHERE id = 1024`。它们不扣库存，不改数据，只是看一眼。但在 48 万 QPS 的压力下，每多看一眼就多一条 SQL，多一条 SQL 就多一个数据库连接排队。

"让这些读请求别碰数据库了。"团队的第一次演化从这里开始。

### 引入 Redis 作为读缓存

架构上多了一层：

```
应用服务器 → Redis（读缓存） → MySQL（只负责写）
```

代码改动出奇地小：

```java
public Product getProduct(Long productId) {
    // 1. 先查 Redis
    String cacheKey = "product:" + productId;
    Product cached = redis.get(cacheKey);
    if (cached != null) {
        return cached;
    }
    
    // 2. Redis 没命中，查数据库
    Product product = dao.selectById(productId);
    if (product != null) {
        redis.set(cacheKey, product, 60, TimeUnit.SECONDS); // 缓存 60 秒
    }
    return product;
}
```

这就是经典的 Cache-Aside 模式。逻辑简单、行为确定的，部署之后效果立竿见影：打到数据库的 QPS 从 48000 直接降到了大约 6000。数据库的 CPU 从 100% 降到了 30%，连接池的水位终于退了。

那天晚上团队的钉钉群里，第一次出现了竖大拇指的表情。

但这种快乐持续了不到两个小时。

### 新问题浮现：缓存穿透

凌晨两点，运维发现数据库的 CPU 又开始往上走。不是秒杀商品——那 1000 台早抢完了。是一批奇怪的查询：

```sql
SELECT * FROM product WHERE id = 99999;
SELECT * FROM product WHERE id = 88888;
SELECT * FROM product WHERE id = 77777;
...
```

这些商品 ID 根本不存在。但缓存里也没有它们的数据（因为从来没人查过）。于是每个查询都穿透缓存，结结实实地砸在了数据库上。

更糟糕的是，这些查询不是来自普通用户。安全团队后来追踪到，这是一个竞争对手雇的"攻击者"——他们写了一个简单的脚本，用随机商品 ID 疯狂查询秒杀接口。脚本的目的不是抢东西，是拖慢系统。

**一万个 `WHERE id = (随机数)`，每一个都会穿透缓存。**

因为目标 ID 在数据库里根本不存在，`dao.selectById()` 返回 `null`。而上面的代码里——仔细看——当 `product` 为 `null` 的时候，**没有把 `null` 写入缓存。**

这不是 bug，这是直觉：一个不存在的东西，缓存它干嘛？

但就是这个直觉，留下了一个漏洞。攻击者正是利用了这一点——每一个"不存在"的查询都变成了一次真实的数据库访问。

### 修第一个洞：缓存空值

最简单的修复：哪怕查出来是 `null`，也缓存一下。

```java
if (product != null) {
    redis.set(cacheKey, product, 60, TimeUnit.SECONDS);
} else {
    redis.set(cacheKey, "NULL", 30, TimeUnit.SECONDS); // 空值也缓存，但时间短一点
}
```

这样，攻击脚本的随机 ID 第一次穿透之后，接下来的 30 秒内同样的 ID 就会被 Redis 里的 `"NULL"` 拦住，不会再碰数据库。

临时止血。但团队心里明白，这不是根本解——如果攻击者每次都用新 ID 呢？30 秒之后又来一轮呢？缓存的 `"NULL"` 值会越来越多，最终可能挤爆 Redis 的内存。

根本的解决方案——布隆过滤器——我们留给第 2 章专门讲。眼下，系统至少不会在凌晨两点因为脚本攻击而崩盘了。

### 这一轮演化的收获

用 Redis 做读缓存，解决了 87% 的无效数据库访问。但这次演化的真正价值不是引入了 Redis——Redis 谁都会用——而是暴露了一个重要的认知模型：

> **缓存是一面盾牌。盾牌的特点是：你知道它挡在哪儿，你就知道攻击会打在哪儿。**

第一次演化的盾牌，挡住了合法用户的反复刷新，但没有挡住恶意用户的无效 ID。盾牌的边界，就是你下一次要修补的位置。

---

但读的问题解决之后，一个更深的问题浮出了水面：**写怎么办？**

缓存只能挡在前面帮数据库分担读的压力。但每次有人抢到商品，还是要执行一次 `UPDATE seckill_stock SET sold_count = sold_count + 1`。这个 `UPDATE` 依然要加行锁，依然只能串行执行。

数据库现在不忙了——但瓶颈还是那行锁。1000 台手机可能 30 秒就卖完了，但这 30 秒内的并发请求依然能把连接池打满。

读的问题解决了。写的问题要换个思路。

## 1.5 第二次演化：库存预扣 + 异步下单

到目前为止，每一笔秒杀订单的实际卡点都在这里：

```sql
UPDATE seckill_stock
SET sold_count = sold_count + 1
WHERE product_id = 1024
  AND sold_count < total_count;
```

这条 SQL 在任何时刻只能有一个人在跑。你加再多应用服务器、再多数据库从库，也改变不了这个事实。因为库存扣减不是读操作——它不能随便分流。

团队坐下来开会。白板上画了三个圆圈：MySQL、Redis、消息队列。

产品经理问："MySQL 的 UPDATE 一秒最多能跑多少次？"

"不排队的情况下，七八百次。"后端负责人说。"但如果考虑到上下文切换和锁等待，实际极限大概四百次。"

"Redis 呢？"

"Redis 的 INCR 是单线程执行的，内存操作——一台普通的 Redis 实例，一秒大概能跑 10 万次。"

会议室安静了两秒。

"那为什么不直接用 Redis 扣库存？"

### 把库存"搬"到 Redis

方案如下：

1. 秒杀开始前，把库存总数（1000）加载到 Redis：`SET seckill:stock:1024 1000`
2. 用户请求到达时，不碰 MySQL，直接对 Redis 执行 `DECR`：

```java
public OrderResult seckill(Long productId, Long userId) {
    String stockKey = "seckill:stock:" + productId;
    Long remaining = redis.decr(stockKey);
    
    if (remaining < 0) {
        // 库存已经扣到负数了，恢复并返回售罄
        redis.incr(stockKey);
        return OrderResult.soldOut();
    }
    
    // 扣减成功！但注意——此时订单还没创建
    sendOrderMessage(userId, productId);
    return OrderResult.queued();
}
```

关键变化：`DECR` 返回负数说明库存已经没了。Redis 的 `DECR` 是原子操作，10 万个并发请求同时执行，Redis 会乖乖地把它排成队，一个一个减。没有行锁，没有连接池，没有上下文切换风暴。

一台 Redis 实例，单线程，内存操作，四行代码。库存扣减整整齐齐。

然后在 `remaining >= 0` 的时候，不直接创建订单，而是发一条消息到消息队列：

```
订单消息: { userId: 张三, productId: 1024, timestamp: 00:00:00.123 }
```

订单消费者——部署了 20 个实例——从 MQ 中拉取消息，每个消息执行一次 `INSERT INTO orders`。消费者可以控制消费速度：每秒 500 条、1000 条，完全按数据库的承受能力来。

架构变成了这样：

```
用户请求 → Redis (DECR 扣库存) → MQ (订单消息) → 消费者 → MySQL (创建订单)
```

流量尖峰在 Redis 这一层就被削平了。MQ 天然是缓冲区——生产者可以一秒扔进来 10 万条消息，消费者按自己的节奏慢慢消化。

### 新问题：库存回滚的困境

上线后的前两次秒杀非常成功。活动在几秒内结束，没有一次宕机。

但第三次，出问题了。

一个用户的请求走到了 `redis.decr()`——扣减成功，`remaining` 返回 500，大于 0。Redis 上库存从 501 变成了 500。

然后，`sendOrderMessage()` 调用了消息队列的发送 API。

MQ 集群刚好在那 300 毫秒进行 leader 切换。消息发送超时。

代码里没有对这个超时做特殊处理。异常被全局异常处理器捕获，返回了 `500 Internal Server Error`。

用户看到报错，刷新页面，重新抢了一次。这次成功了。

但问题来了：Redis 上的库存已经从 501 变成了 500。那第一次失败的尝试，扣掉的 1 个库存，没有对应的订单。

**库存扣了，订单没创建。这一件商品凭空消失了。**

这就是"库存预扣"方案最大的软肋：**Redis DECR 成功了，不代表后续流程一定会成功。** 消息队列可能超时、消费者可能崩溃、数据库可能死锁——任何一个下游环节失败，都意味着"扣了库存但没生成订单"。

### 补偿方案：对账 + 回补

团队加了两个补救措施：

**措施一：定时对账。** 每 5 分钟跑一个任务——统计 Redis 里扣了多少库存，数据库里实际创建了多少订单。差额就是丢失的库存，手动回补到 Redis。

**措施二：超时释放。** Redis 里预扣的库存加一个 15 分钟的 TTL。如果 15 分钟内没有对应的订单入库，库存自动回补。

这两个措施都是"事后弥补"，不是"事前保证"。团队知道这一点，但业务上这是可接受的——偶尔一两件商品对不上账，可以通过客服补偿用户。相比"整个平台宕机三小时"，丢一两件库存在可容忍范围内。

这就是工程中的取舍：**用事后补偿换极致的写入吞吐量。** 不是最优雅的方案，但在那个时间节点上，是对的方案。

> 关于库存回滚和数据一致性的完整解决方案，将在第 12 章（分布式事务实战）中详细展开。眼下的方案能活，但活得不够好。

### 这一轮演化的收获

把库存扣减从 MySQL 搬到 Redis，是一个思维转折点：

> **瓶颈不一定要被"消除"，也可以被"绕过"。**

MySQL 的行锁是物理规律——它就该那么慢。你没有必要和物理规律较劲。Redis 没有行锁问题，是因为它用了完全不同的并发模型（单线程事件循环 + 内存操作）。既然 Redis 更适合这个场景，那就把库存"搬过去"。

但代价也很明显：**你把一个原来在事务边界内的事，拆到了两个独立系统里。** Redis 扣库存是一个系统，MQ 发消息是另一个系统，MySQL 创建订单是第三个系统。每一个系统都可能独立失败。原来数据库事务帮你保证了"要么全成功，要么全回滚"，现在这个保证没了，需要你自己去修补。

这就是分布式系统的一个核心命题——以后再讲。

眼下，系统活下来了。但那是对"什么时候结束"的感知还不够——Redis DECR 这个方案虽然快，但如果任何人都能在一瞬间把库存从 1000 减到 0，那"公平性"怎么办？普通用户和黄牛脚本站在同一条线上吗？

第三个问题，正是下一次演化的起点。

## 1.6 第三次演化：队列削峰 + 令牌桶

Redis DECR 方案上线后，系统稳了。每一次秒杀都在 30 秒内干净利落地结束，不再有宕机，不再有 500。

但用户投诉换了一种方式出现。

"为什么我 00:00:00 点下去的，没抢到？"

"我朋友在我后面点的，他抢到了，我没有。"

"是不是有机器人？普通人根本抢不到吧。"

### 公平性的裂缝

回看 Redis DECR 方案，它的逻辑是：谁先到达 Redis，谁就先扣库存。谁的网络快、谁的机器离服务器近、谁的脚本优化得好——谁就赢。

一个坐在杭州的普通用户，手指点击 → 手机发送 HTTP 请求 → 经过小区基站 → 经过运营商骨干网 → 到达数据中心 → Nginx → 应用服务器 → Redis。这一路下来，光网络延迟就有 30-50 毫秒。

而黄牛的脚本部署在数据中心隔壁的一台云服务器上。网络延迟：0.3 毫秒。

这就像百米赛跑——普通人从起跑线出发，黄牛从 95 米处出发。而队列方案相当于：所有人先到等候区集合，裁判喊"各就各位"之后同时放行，让实际扣库存的顺序不再取决于谁的网络更快。

Redis DECR 解决了"系统会不会死"的问题，但没有解决"谁来扣这一下"的问题。它本质上是一个**先到先得**的模型，而"先到"取决于物理世界的不平等：网络延迟、服务器位置、硬件性能。

能不能让"先到先得"变成"大家一起排队，公平抽签"？

### 引入队列：从"抢"到"排"

新方案的思路：

1. 用户请求到达后，不直接扣库存，先进入一个队列
2. 队列按照固定的速率被消费
3. 消费到的请求才真正执行 Redis DECR

这样一来，一百万个请求在零点的第一毫秒涌入，它们做的第一件事不是冲向 Redis 开始拼刺刀，而是乖乖取一个排队号码。消费端以每秒 5000 个请求的速度从队列里取任务、执行 DECR。

这对用户意味着什么？意味着你在 00:00:00.001 点下的请求，和黄牛脚本在 00:00:00.001 点下的请求，进入了同一个队列。你们都需要等——不再是比谁快，而是比谁先入队、先处理。

具体实现可以用 Redis 的 List 数据结构：

```java
// 用户请求到达
public OrderResult seckill(Long productId, Long userId) {
    String queueKey = "seckill:queue:" + productId;
    
    // 把用户 ID 推到队列尾部
    redis.rpush(queueKey, userId.toString());
    
    return OrderResult.queued("您已进入排队，请等待结果...");
}
```

消费端：

```java
// 消费端：按固定速率消费队列
public void consumeQueue(Long productId) {
    String queueKey = "seckill:queue:" + productId;
    String stockKey = "seckill:stock:" + productId;
    
    while (true) {
        String userId = redis.lpop(queueKey);
        if (userId == null) break;
        
        Long remaining = redis.decr(stockKey);
        if (remaining < 0) {
            redis.incr(stockKey);
            notifyUser(userId, "已售罄");
            continue;
        }
        
        sendOrderMessage(Long.valueOf(userId), productId);
        notifyUser(userId, "抢购成功！");
    }
}
```

用户端的行为变了：不再是点下去立刻知道结果，而是点下去之后进入一个等待页，几秒后收到结果通知。

### 为什么要加令牌桶

队列解决了公平性问题——所有人站在同一条起跑线上。但一个新的问题浮现了：消费速率设多少？

设 1000/s？那 100 万人的队列要消费 1000 秒（16 分钟）。用户不可能等 16 分钟。

设 10000/s？那数据库的订单创建扛不住（消费者最后还是要写 MySQL）。

我们需要一个更精细的控速机制。令牌桶应运而生。

**令牌桶的直觉非常朴素：**

想象一个水桶，桶的容量是 1000 个令牌。一个叫"令牌工厂"的线程以每秒 2000 个的恒定速度往桶里放令牌。桶满了就停止放。

消费端从队列里取请求之前，必须先从桶里拿一个令牌。拿到令牌才能执行 DECR。拿不到令牌就等——等多长时间？等到下一个令牌被生产出来。

```java
// 消费端：令牌桶控速版
RateLimiter limiter = RateLimiter.create(2000); // 每秒 2000 个令牌

public void consumeQueue(Long productId) {
    String queueKey = "seckill:queue:" + productId;
    String stockKey = "seckill:stock:" + productId;
    
    while (true) {
        // 先拿令牌，拿不到就阻塞等待
        limiter.acquire();
        
        String userId = redis.lpop(queueKey);
        if (userId == null) break;
        
        Long remaining = redis.decr(stockKey);
        if (remaining < 0) {
            redis.incr(stockKey);
            continue;
        }
        
        sendOrderMessage(Long.valueOf(userId), productId);
    }
}
```

`RateLimiter.create(2000)` 保证了——无论队列里有多少请求在等——**每秒最多只有 2000 个请求有机会碰 Redis 的库存。** 其余请求在 `limiter.acquire()` 这一行被均匀地分散到了时间轴上。

这就是令牌桶的哲学：**不拒绝任何人，但也不让任何人冲得太快。** 它不是"限流用户"，而是"保护下游"。消费者（MySQL 订单入库）每秒只能消化 2000 条，那令牌桶就确保上游（Redis DECR）每秒最多发 2000 条。无论洪水多大，下游感受到的永远是涓涓细流。

### 用户的感知

用户端的变化：

- **点下"抢购"按钮** → 立刻返回"您已进入排队通道"
- **页面进入等待状态** → 显示排队序号，估计等待时间
- **几秒到十几秒后** → 收到结果（抢到了 / 已售罄）

慢吗？比原来"点击即扣库存"慢了几秒。但公平吗？所有人都在排队，黄牛和普通用户站在同一条线上。

团队做了一个 A/B 测试：50% 流量走"直接 DECR"方案，50% 流量走"队列 + 令牌桶"方案。结果：

- 直接 DECR 方案：成功订单中脚本和机器人的占比 94%
- 队列 + 令牌桶方案：成功订单中脚本和机器人的占比 32%（即普通用户占 68%）

差距不是因为技术，而是因为队列抹平了物理网络的不平等。

### 令牌桶的一个微妙点

`RateLimiter.create(2000)` 的行为有一个值得了解的特性：**它不是每 1/2000 秒（0.5ms）发一个令牌——它支持"突发"。**

如果过去一秒内没有任何请求，令牌桶里会积攒最多 1000 个令牌。当下一波请求突然到达时，这 1000 个令牌可以被瞬间消费掉。这就是"桶"的含义——你可以短暂地超过平均速率，但不能持续超过。

这个特性在秒杀场景中非常有用：零点那一刻的流量确实是"突发"的。前 1000 个请求可以瞬间通过，让用户感觉不到明显的等待。之后的请求才被均匀摊开到时间轴上。

但如果把桶容量设为无限大——那就退化成了不加限制的直接 DECR。所以桶容量（burst size）是一个需要仔细斟酌的参数：太小，用户排队时间太长；太大，保护下游的效果减弱。团队最终选择了 `（消费速率）/ 2` 作为桶容量，也就是 1000。这意味着队列里的第一个 1000 人几乎不需要排队。

---

现在，系统经历了三次演化：

1. **读缓存（Redis）** — 让 87% 的读请求不再碰数据库
2. **写分离（Redis DECR + MQ）** — 让库存扣减不再被 MySQL 行锁卡死
3. **队列削峰 + 令牌桶** — 让流量波浪变成均匀水流，兼顾公平与保护

三次演化解决了一个问题：**活下来了，而且活得还算像样。**

但如果你往回看，这三次演化背后有一条隐藏的主线——每一步都引入了**排队**。行锁是 MySQL 帮你排队，Redis DECR 是 Redis 帮你排队（单线程事件循环），队列削峰是应用层显式的排队。

似乎在"三高"系统里，排队永远绕不过去。这不是偶然。

下一节，我们从排队论的角度回头审视这一切——看看有没有一个统一的数学视角，能解释为什么排队是唯一的出路。

---

## 1.7 原理沉淀：排队论视角下的并发控制

如果你回到本章开头，重新看一遍三次演化，你会发现一个规律：

- 第一次演化（Redis 缓存）：读请求被缓存挡在外面，**减少了到达数据库的请求数量**
- 第二次演化（Redis DECR + MQ）：写请求被 Redis 串行化 + MQ 缓冲，**平滑了到达数据库的尖峰**
- 第三次演化（队列 + 令牌桶）：请求被显式排队，**限定了到达下游的速率**

三次演化，本质上都在做同一件事：**控制"到达速率"，让它不超过"处理能力"。**

这三个字听起来简单到几乎不值一提。但排队论用一条公式，把这件事说清楚了。

### Little 定律：L = λW

排队论里最核心的公式叫 Little 定律（Little's Law），由 MIT 的 John Little 在 1961 年证明。它长这样：

```
L = λ × W
```

其中：

- **L**：系统中平均存在的请求数（正在处理 + 正在排队）
- **λ**：请求到达速率（每秒来多少个）
- **W**：每个请求在系统中平均停留的时间（排队时间 + 处理时间）

这个公式的一个迷人之处是：**它对任何排队系统都成立。** 不管队列是 FIFO 还是 LIFO，不管服务时间是指数分布还是固定值，不管有几个服务窗口——只要系统处于稳定状态，L = λW 一定成立。

我们把它翻译成秒杀场景的语言：

- L：数据库连接池里被占用的连接数
- λ：每秒打到数据库的写请求数
- W：数据库处理一个写请求的时间

把秒杀场景代入 Little 定律，对比稳定态和非稳定态：

| 状态 | λ（到达速率） | W（停留时间） | L（系统中请求数） | 连接池容量 | 结果 |
|------|-------------|-------------|-----------------|-----------|------|
| 稳定 | 1000/s | 1ms | 1 | 2000 | 正常 |
| 理想高并发 | 100000/s | 1ms | 100 | 2000 | 接近满载 |
| 雪崩 | 100000/s | 30s | 3,000,000 | 2000 | 崩溃 |

关键在于 W。当连接池耗尽、上下文切换风暴来临，W 从 1ms 膨胀到 30 秒——不是线性增长，是三个数量级的跳变。L = λW，λ 已经极高，W 再炸裂，系统里的请求数瞬间超过连接池容量的 1500 倍。雪崩不可避免。

### 削峰：主动增大 W，换取 λ 可控

Little 定律揭示了两个控制变量：

- **你可以降低 λ**（让到达的更少）→ 缓存、限流
- **你可以增大 W**（让它们等得更久）→ 排队、令牌桶

第二次演化和第三次演化，本质上都是**主动增大 W**。

在第二次演化中，MQ 的消费者以固定速率消费——每个请求在 MQ 里多等了 200ms。W 变大了。

在第三次演化中，`RateLimiter.acquire()` 让每个超过速率上限的请求均匀地等待。W 更大了。

但代价是有回报的：因为 W 变大了，λ 被平均化到了时间轴上。在令牌桶的保护下，Redis 感受到的 λ 不再是 100000 QPS 的尖峰，而是匀速的 2000 QPS。

```
稳定态：L = 2000 × 0.001 = 2
```

系统里同时只有 2 个请求。连接池有 100 个。CPU 在 15%。一切安然无恙。

这就是削峰的本质：**主动牺牲"即时性"（增大 W），换取"稳定性"（降低 λ）。**

### 排队是唯一的出路吗？

回过头看，你会发现一个残酷的事实：在"三高"场景里，你没有任何办法让大量并发请求"同时处理"。因为物理世界只有一个 CPU、一块磁盘、一条网络通道。它们天然是串行的。

串行意味着排队。排队意味着等待。

你能做的，不是在"排队"和"不排队"之间选择——排队是物理规律决定的。你唯一能选的，是**在哪里排队、怎么排队、等多久**：

| 方案 | 排队的位置 | 排队的管理者 | W（等待时间） |
|------|-----------|-------------|-------------|
| MySQL 行锁 | 数据库连接池 | InnoDB 锁管理器 | 不可控，可能 30 秒 |
| Redis DECR | Redis 事件循环 | Redis 单线程 | 可控，微秒级别 |
| 队列 + 令牌桶 | 应用层队列 | RateLimiter | 精确可控，毫秒级别 |

每一次演化，都是把排队从**不可控的位置**（MySQL 连接池）搬到**可控的位置**（应用层队列），把等待时间从**随机的灾难级**变成**均匀的可容忍级**。

### 从"术"到"道"

本章走了很远：从一个 `UPDATE` 语句开始，经历了缓存、Redis DECR、MQ、队列削峰、令牌桶。每一层都引入了新的技术、新的代码、新的配置参数。

但所有这些技术的底层，是同一个数学事实：

> **当一个系统的并发需求超过了串行处理能力时，排队是唯一的选择。工程的价值不在于消除排队，而在于让排队变得优雅。**

第 2 章我们会看到，这个原则不只适用于秒杀。缓存、分布式锁、消息队列——整个"三高"体系，本质上都是一门"把排队放到对的地方"的艺术。
