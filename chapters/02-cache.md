## 2.3 三种崩塌：穿透、击穿、雪崩

> **写作提示**：合并讲是因为这三个名字"长得像"，初学者总记混——但它们的根因和解药完全不同。
> **结构建议**：先用一张三栏对比表立住区别（触发条件 / 受害对象 / 解药方向），然后逐个用 2-3 段事故展开。
> 布隆过滤器的"几何直觉"放在穿透小节，用"彩色球扔进桶"的类比替代误判率公式推导。
> 雪崩的"立体防御"中提一句熔断，详细机制走第 6.3 节，不展开。

### 三栏对比

| 名字 | 一句话 | 触发条件 | 解药方向 |
|---|---|---|---|
| 穿透 | 查的东西**不存在** | 恶意/随机查不存在的 key | 布隆过滤器、空值缓存 |
| 击穿 | 查的东西**刚刚消失** | 热点 key 过期瞬间 | 互斥锁、永不过期 |
| 雪崩 | 查的东西**集体消失** | 大批 key 同时过期 / 缓存集群挂了 | 随机 TTL、多级缓存、熔断降级 |

- [ ] 三栏对比表（先立住区别）
- [ ] 缓存穿透：恶意查询 + 布隆过滤器的几何直觉
- [ ] 缓存击穿：热点过期 + 互斥锁 vs"永不过期 + 异步更新"
- [ ] 缓存雪崩：批量过期 + 随机 TTL + 立体防御（提一句熔断 → 6.3）
- [ ] 三个故事最后回到同一个结论："缓存只是把问题挪到了更远的地方"

## 2.4 缓存一致性：十年争论的起点

> **写作提示**：本节负责"立问题"——为什么这事儿能吵十年？
> 用一个最朴素的例子：库存从 100 改到 99，要不要先删缓存再更新 DB？还是先更新 DB 再删缓存？
> 看似只有两种选择，每种都有诡异的失败模式。
> 这是一个"无论怎么选都有 bug"的入口，也是 2.5 节工程妥协方案的起点。

- [ ] 一个朴素的更新场景
- [ ] 方案 A：先删缓存再更新 DB——读旧值的时间窗口
- [ ] 方案 B：先更新 DB 再删缓存——并发读+写的诡异交错
- [ ] 为什么"再加一道锁"也不能根治
- [ ] 立住矛盾：无论怎么选都有 bug
