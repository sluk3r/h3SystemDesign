# 设定圣经：橙舟（ChengZhou）

> **本文件定位**：全书共享的"虚拟公司 + 虚拟团队 + 虚拟系统"设定，是所有章节场景描写的**单一来源**。
>
> **写作铁律**：
> - 人物名、服务名、事故年表**只能从本文件取**，不在章节里临时造。
> - 设定的修改只在本文件做；章节文件只引用，不发明。
> - 对应不上的细节（比如某个章节需要一个本文件没列的服务），先回到本文件加，再去章节里用。
>
> **类比**：本文件之于全书，约等于 [Spring PetClinic](https://github.com/spring-projects/spring-petclinic) 之于 Spring 全家桶教程——一个稳定的"认知坐标系"，让读者跨章不迷路。

## 3. 团队人物卡

> **使用规则**：每章场景中出现具体人物时，**优先**从本表挑选。新人物只在"案例当事人 / 一次性对白"时引入，不进入本表。

> - **老张** 贯穿全书，是默认在场的"灵魂角色"；其余四人按场景需要灵活搭配

## 4. 标准服务清单

> **使用规则**：每章场景中提到具体服务时，**优先**使用核心 12 个；如确需新增，先回本文件加（不要临时造名字）。
>
> 服务名锁定的好处：读者跨章读到 `stock-service` 时立刻知道是哪个，不用每章重新认识。

### 4.1 核心 12 个（确定会反复出场）

| 服务名 | 一句话 | 关键特征 / 主要登场章节 |
|---|---|---|
| `api-gateway` | 自研 API 网关（Java / Netty） | 认证、限流、路由、降级；几乎每章都出现一句 |
| `auth-service` | 认证 / 会话 | Redis 存 token；典型的"缓存依赖型"服务（→ 第 2 章） |
| `user-service` | 用户主数据 | MySQL 分 32 库，按 user_id 取模（→ 第 4 章） |
| `product-service` | 商品详情 | MySQL 分 64 库（基因法）；多级缓存（→ 第 2、4 章） |
| `stock-service` | 库存扣减 | **本书最常出场的服务**；2016 行锁雪崩重生；现在 Redis 主 + MySQL 兜底（→ 第 1、3、9 章） |
| `price-service` | 价格服务 | 强一致写、读多写少；2026 序幕主从切换的那个（→ 第 7、11 章） |
| `order-service` | 订单 | 全公司事务最复杂；用 Saga；2019 重复下单事故主角（→ 第 11、12 章） |
| `payment-service` | 支付（内部） | 对接第三方支付通道（→ 第 12 章） |
| `payment-notify` | 支付回调 | 强幂等；序幕里"熔断 half-open"的那一站（→ 第 6、11 章） |
| `notify-service` | 短信 / Push / 站内信 | 跨机房调用代表（杭州→上海）（→ 第 7 章） |
| `recommend-service` | 推荐 | JVM 重负担；序幕"GC 420ms"那一站（→ 第 8、10 章） |
| `member-service` | 会员等级 / 会员价 | 写少读多，强缓存依赖（→ 第 2 章） |

### 4.2 中间件

| 名称 | 实例 | 备注 |
|---|---|---|
| MySQL 集群 | 主从 + Group Replication | DBA 王姐主守 |
| Redis Cluster | 多套（按业务隔离） | 缓存层主力 |
| RocketMQ | 多 broker | 解耦 / 削峰；2018 缓存血案有它的角色 |
| ZooKeeper | 服务注册（Dubbo 时代）+ 分布式锁场景 | 第 3 章主角之一 |
| Elasticsearch | 搜索 + 日志 | 双角色 |

下列服务在某章首次需要登场时，再决定是否升级进核心列表。**临时使用前必须先回本节登记**，避免名字漂移。

## 6. 历史事故锚点

> 这些事故是全书反复引用的"共享回忆"。每条**只锁定一句根因 + 一句教训 + 主讲章**——具体细节（止损过程、复盘报告、技术演化）由各主讲章节自行展开，避免和正文重复。
>
> 写法约定：在章节中第一次提及时用全名（如"2018-03 缓存血案"），后续可简称（"那次缓存血案"）。

| 事故 | 一句根因 | 一句教训 | 主讲章 |
|---|---|---|---|
| **2016-11-11 行锁雪崩** | 秒杀走 MySQL 行锁，48 万 QPS 下队列堆积全站雪崩 | 高并发写不能直接打数据库 | 第 1 章 |
| **2018-03 缓存血案** | Redis Cluster 槽位变更触发大量 key 不可达，DB 被打挂 | 缓存层是脆弱依赖，任何变更都要走金丝雀 | 第 2 章 2.3 + 第 6 章 |
| **2019-双十一 重复下单** | 网关重试 + Saga 幂等 key 漏洞，订单被创建多次 | 全链路幂等不是补丁是基础设施 | 第 11 章 11.4 + 第 12 章 |
| **2022-05 张北脑裂** | 专线抖动 27 秒，MGR 两侧各选出主，写入双向冲突 | 多活的代价是 CAP 三选二的痛 | 第 7 章 7.4 |
| **2025-09 对账日** | 事件投递 0.03% 概率丢失，积月累计差额破百万 | 没有对账的"最终一致"是空头支票 | 第 11 章 11.5 |
| **2026 47 分钟尾延迟**（序幕） | 主从切换 + GC + 熔断探测 + MQ 再平衡四因素叠加 | 没报警没崩溃的故障最难发现 | 序幕 + 第 8 章 8.4 |

## 7. 写作守则速查

| 守则 | 一句话 | 反例 |
|---|---|---|
| **人物锁定** | 出现人物只从 §3 选 | 突然冒出"工程师老李说……"——回去改成老张/小林 |

## 9. 本书故意不写的角色 / 视角

> **存在的意义**：明确边界，避免读者期待落空，也避免写作时被各种"也应该写一下吧"的诱惑拖走重心。

### 9.1 不出现的角色

| 角色 | 为什么不写 |
|---|---|
| 算法工程师 / 数据科学家 | 本书聚焦"系统是如何撑住流量、抗住故障、对住数据"的，不展开推荐/搜索的算法细节 |
| 前端 / 客户端工程师 | 仅在序幕和第 8 章 TTFB / FCP 出现一次"前端也有自己的故事"作为对照，不展开 |
| 产品经理 / 业务方 | 偶尔以"业务侧提了个需求"的方式出现，但不出现具名 PM；本书的"反派"是问题本身，不是人 |
| 高管 / VP / CTO | 不写自上而下的战略叙事；本书是工程师视角的"一线探险" |

### 9.2 不展开的话题

| 话题 | 为什么不展开 |
|---|---|
| 公司内部政治 / 部门博弈 | 真实存在但不是本书主题；偶有一句"另一个团队不同意"作为约束条件即可，不展开 |
| KPI / 晋升答辩 / 绩效 | 不写——本书希望读者忘掉这些噪声，直面"问题怎么被解决" |
| 招聘 / 团队管理 / OKR | 不写——这是另一本书该做的事 |
| 具体框架的版本选型大战 | 出现在事故复盘里时只一笔带过（如"我们当时用的还是 Dubbo 2.x"），不展开技术选型论战 |

### 9.3 写作时的边界自检

写一段场景之前先问一句：**这段是在讲"问题如何被解决"吗？** 如果偏向以下任何一个方向，停下来：

- 在写"某某领导说……"——不写
- 在解释"为什么我们部门要做这个"——不写
- 在罗列某个框架的所有特性——本书是问题驱动的，不是技术宣传册

## 10. 对话语调示范（calibration）

> **使用规则**：写人物对话之前先来这里读一遍。这一节的目的不是穷举所有对话，而是让"老张的镇定到什么程度"、"小周的傻气和机灵的边界"这些感觉**有据可依**。

### 10.1 老张：镇定 + 故事感 + 偶尔扎心

**✅ 标准款**：

> 老张端起咖啡，往后一靠："这事儿我们 2018 年踩过坑——那次大家都不敢碰 Redis 配置。"

> 老张盯了一会儿监控曲线，没说话。过了大概十秒钟才开口："先把入口流量切到 80%。出问题再说更多的话。"

**⚠️ 偏过头（避免）**：

> ❌ 老张拍着桌子吼："这是大事故！谁干的！"
>   ——老张不会失态，他不"演 SRE"，他**就是** SRE。

> ❌ 老张语重心长地说："孩子，你要明白，分布式系统的本质是……"
>   ——不要让老张"教书"。他只在白板上画图，不发表演讲。

### 10.2 小林：认真 + 倔 + 有 commit 的人

**✅ 标准款**：

> 小林皱眉："我先复一下 commit 再下结论。" 他翻了几下 IDE，"是 2019 年 11 月加的，那次活动赶时间，加了个 fallback 没删。"

> 小林："不对，这段逻辑我一周前刚改过。" 他顿了一下，"我去看下生产分支。"

**⚠️ 偏过头（避免）**：

> ❌ 小林大喊："这不是我的锅！"
>   ——小林倔在"对自己代码负责到底"，不是甩锅。

### 10.3 小周：好奇 + 提问要害 + 不假装懂

**✅ 标准款**：

> 小周犹豫了一下："为什么要 rebalance？我没看明白。"

> 小周倒吸一口凉气："那不就是脑裂？"
>   ——这种"歪打正着、点破要害"的提问是小周最重要的功能。

> 小周把手机放下："等等——书上说幂等是用唯一索引兜底，但这里没有唯一约束怎么办？"
>   ——读过书但没线上经验，问的问题"看似基础，实则关键"。

**⚠️ 偏过头（避免）**：

> ❌ 小周："我觉得这里应该用 CRDT 来解决冲突。"
>   ——小周不是"已经懂分布式系统的研究生"，他是"知道 CRDT 这个名词但没用过、需要被引导"。

> ❌ 小周："好的老张，我懂了！谢谢老张！"
>   ——小周不是工具人；他听完讲解会**追问**或**联想**，不会傻笑结束。

### 10.4 王姐：直接 + 护数据 + 不留情面

**✅ 标准款**：

> 王姐看了一眼 SQL："这个 DDL 不能在白天上。下班后再说。"

> 王姐："数据是命，应用是工具。你们要 truncate 这张表？再确认三遍。"

**⚠️ 偏过头（避免）**：

> ❌ 王姐："我建议……"
>   ——王姐很少"建议"，她直接说"不行"或"可以"。

### 10.5 多人对话节奏

**✅ 标准款**（三人节奏）：

> 老张指着监控："切到 80% 之后，曲线还在涨。"
>
> 小林："是不是有缓存击穿？我看一下命中率。"
>
> 小周（小声）："为什么 80% 还会涨？流量不是少了 20% 吗？"
>
> 老张笑了一下："因为剩下的 80% 全在打数据库。"

**节奏要点**：
- 三人最多。第四个人发言读者会乱。
- 小周的"小声"或"犹豫"提示是常用的，因为他对自己的判断没把握。
- 老张作为定锚人，最后一句话经常是结论性的或者带轻微的幽默感。
